企业级数字员工

让 Agent 少走重复的路：将企业高频任务提炼为 Fast-workflow

2026年9月20日
|

从每天几十份日报的真实执行轨迹中提炼 LLM inside 脚本，观察 Agent 提速效果，并记录异常接管与先回执后检查的实践。

在我们的交付团队里，一个具备自主规划和工具调用能力的 Agent，每天要通过钉钉收集几十位同事的日报。它需要理解工作内容、核实身份、更新多维表，再给出收讫回执；遇到缺项继续追问，执行失败则查证并恢复。

功能已经能用，但单次处理偏慢。有一个真实任务，完整执行用了14分38秒，外围 Agent 发起72次工具调用。每天几十份日报重复走过类似过程，让我们开始追问：哪些判断必须每次做，哪些执行路径已经可以复用？

于是，我们分析最近的执行轨迹，将反复出现的步骤和判断沉淀为内嵌 LLM 的脚本，再交回原有 Agent 使用。这是一次从企业高频任务中提炼 Fast-workflow 的实验。

从慢任务中，找出可以复用的路径

我们把真实消息、工具调用、返回结果和最终写入串起来，对照多次任务。开头那次14分38秒的执行中，Agent 不仅加载技能，还分段阅读身份核验和归档脚本源码，查询命令帮助，临时编写 Python 处理分页，随后写入、回读，再完成知识库归档和消息回复。

这说明，当时已经有单点脚本，但外围仍需自己探索和编排它们。当然，72次调用并非全是浪费，后续归档也属于实际工作。我们要识别的是其中已经稳定、可以不再临时组织的部分。

日报也不是简单的文本写入。例如，同事先发工作内容，稍后补一句“8小时”，再确认项目。这几条消息应合并进同一天的同一条记录；“改成7小时”要替换旧值，不能累加；重复消息也不能再次创建日报。

对照成功与失败案例后，我们整理出常见路径：核验身份和日期 → 查询已有日报 → 理解本次变更 → 校验与合并 → 写入 → 回读。 每个节点都要明确输入、动作、继续条件和异常分支。沉淀的是这些执行关系，而不只是一次成功任务的命令列表。

固定步骤用程序，语义判断用 LLM

脚本负责确定性步骤，内部 LLM 负责理解自然语言，返回受 Schema 约束的 JSON：本次是提交还是更正，哪些字段需要变化，对应的原文依据是什么。

例如“项目甲5小时、项目乙3小时”，模型识别工时项，程序负责计算；更新工时时，程序保留已有工作内容。模型输出还需要校验，不能直接作为写入指令。

这样，原本由外围 Agent 逐条组织的工具调用，可以在脚本中连续执行。正常路径的一次语义判断可以覆盖当前消息的多个字段；后续补充或例外仍需继续处理。

这次提炼由开发者和 Coding Agent 共同完成，尚不是 runtime 自动从历史行为中生成并上线工作流。

快速执行、异常接管与回复后检查

我们将脚本作为 fast-workflow 技能放入现有 runtime。外围 Agent 识别日报场景后优先调用它，通过 JSONL 获取进度、保存结果和缺项，再向用户反馈。

缺项是正常业务分支，可以保存已知内容后追问。真正执行失败或超出覆盖范围时，原技能才接管。语义节点失败且尚未写入，可以由外围提供修正 JSON，复用状态继续脚本；写入结果未知，则先查证，不能直接重新创建。

这里还有一个值得保留的做法：脚本完成必要回读 → Agent 先给收讫回执 → 外围继续复核 → 有异常才告知并纠正。

两层检查各有职责。脚本确认写入及回读字段，决定能否说“已经记录”；外围结合原始消息与上下文，检查结果是否准确承接用户意图。

这样，用户可以及时知道已确认的结果，不必等待全部收尾。任务仍能继续检查，正常就不再打扰，异常则主动纠正。它也提醒我们，应分别衡量脚本时间、首次有效回执时间和完整任务时间。

回到真实业务，观察提速效果

我们对照同一批六位提交者相邻两天的日报任务。前一天未调用新脚本，后一天调用了脚本，其中两例进入异常恢复，也保留在样本中。

指标原执行方式引入脚本后
完整任务平均耗时11分50秒6分49秒
平均外围工具调用67.7次32.7次

观察到完整耗时下降约42.5%，外围调用减少约51.7%。这是不同日期、不同输入的前后对比，不能将全部差值归因于脚本。外围调用减少，也不代表底层接口请求同比减少：部分调用被集中到了脚本中。

扩大到9月17日升级后的81个脚本任务，其中52个单次执行、无观测失败且保存回读通过，脚本平均耗时40.4秒。50个有模型明细的正常样本，均一次调用完成。

但40.4秒不能直接与原来的十多分钟相减。这52个任务的完整平均耗时仍为8分18秒，还包含外围核实、归档和收尾；完整任务耗时也不等于用户等待回执的时间。

收益出现了，边界也更清楚了

异常仍然昂贵。81个任务中，19个使用了外围恢复决策，完整耗时平均约15分钟。外围接管后仍会查源码、试参数，恢复过程也需要进一步整理。

质量同样不能只看 Agent 自述。独立回读发现一名成员存在4条相同业务键和来源消息的记录，相关轨迹中有创建后查询未找到、再次创建的动作。这说明，外围兜底也必须遵守写入约束，回复后检查本身也可能漏检。

此外，少调用模型不等于同比节省费用。我们尚未完成完整的前后成本对比，也未单独量化“先回执后检查”的体验收益。

这次实验给我们的方向是：企业高频任务的历史执行轨迹，可以成为改进 Agent 的材料。把已经验证的步骤和判断沉淀下来，后续任务就有机会减少重复探索，同时保留通用 Agent 处理例外的能力。

真实数据让我们看到了机会。接下来，要继续验证哪些路径适合固定、哪些判断应留给模型，以及如何让异常恢复同样可靠、高效。

数据来自2026年9月16日至17日的任务轨迹及后续回读；案例已脱敏。完整任务时间包含回复后处理，前后对比并非严格同输入 A/B 实验。
