企业级数字员工

我们为什么开始给数字员工做“图灵测试”

2026年9月13日
|

当 Agent 真正进入企业工作流，几轮聊天已经不足以证明它可以胜任工作。

这是“企业级数字员工的实践”系列的开篇，写给正在把 Agent 接入消息、文档、日程等真实工作系统的人。

过去我们判断一个 Agent 好不好，最常见的方式是和它聊几句。

问一个问题，看它答得是否正确；再给一个任务，看它是否能说出合理的处理步骤。如果这几轮表现不错，我们很容易得出一个结论：它已经可以用了。

但当 Agent 真正进入企业工作流，这种判断就不够了。

一个数字员工可能很会回答问题，却在群聊中随意插话；可能回复“已经归档”，实际并没有创建任何文档；也可能收到明天的日程后，误以为任务现在就要执行。

如果 Agent 说它完成了，真正需要检查的不是这句话听起来是否可信，而是工作系统中有没有对应的消息、文档、日程或任务结果。这成为我们设计数字员工“图灵测试”的出发点：测评对象不是一段回答，而是工作承诺与平台事实是否一致。

测的不是智能，而是工作

这里说的图灵测试，并不是判断人能否分辨对面是人还是机器。

我们真正想回答的是：当一个 Agent 以员工身份进入协同环境，它能不能看懂正在发生的事情，做出合适的动作，并把结果真正留在工作系统里。

这至少包括几个问题：

  • 什么时候应该回复，什么时候应该保持沉默？
  • 它能否理解当前消息和前文之间的关系？
  • 它是否知道自己的职责、权限和能力边界？
  • 当它说“已经完成”时，对应的消息、文档或日程是否真的存在？
  • 遇到失败或缺少信息时，它会如实说明，还是编一个听起来合理的答案？

这些问题不能只靠阅读提示词来判断，也不能只听 Agent 自己说“我完成了”。答案必须来自工作环境中实际发生的行为。

用成熟度描述“能工作到什么程度”

数字员工不会一步就变成经验丰富的同事。我们更愿意把它的工作能力看成一个逐步提升的过程：

五层成熟度不是能力标签的堆叠，而是一条必须从基础能力逐级验证的工作路径。

  1. 能够参与：在明确指令下完成基础沟通，该回复时回复，不该回应时不抢话。
  2. 能够独立完成：收到一项明确工作后，可以调用工具、留下实际产物，并如实反馈结果。
  3. 能够主动协作：理解多人之间的分工，找到合适的人沟通和交接，推动事情继续进行。
  4. 能够持续负责：不仅完成眼前动作，还会跟进后续变化，处理异常，直到任务真正收口。
  5. 能够积累经验：理解团队和业务背景，复用过去的经验，并持续改进自己的工作方式。

这种分层的价值，不是给 Agent 打一个漂亮的等级，而是帮助我们确定测试顺序。

一个目标是主动协作的 Agent，仍然应该先证明它能够正确参与基础沟通；一个能规划复杂任务的 Agent，如果还会在群里乱回复，就不能因为高级能力看起来不错而跳过基础问题。

从岗位职责和真实问题中生长测试用例

通用标准只能告诉我们大方向，真正有价值的用例来自两个地方。

第一个来源是岗位职责。

如果一个数字员工负责整理共创信息，那么测试就不能停留在“请总结这段内容”。完整的验证应该包括：它是否读懂了输入，是否把结果写入指定位置，写入内容是否正确，以及是否把可核验的结果告诉了用户。

第二个来源是真实问题。

每一次“不该回复却回复了”“说完成但没有产物”“忘记前文”“没有依据却给出确定答案”，都不应该只靠现场修改一句提示词来解决。我们需要把它缩成一个安全、可重复执行的场景，明确输入、结束条件、通过标准和需要回读的证据，然后在后续版本中持续回归。

这样积累下来的测试集，不只是 QA 的资产，也是在记录这个岗位对“把工作做好”的真实要求。

让测试自己在真实环境里跑完

为了验证这套方法能不能真正工作，我们做过一次最小的无人值守 E2E 实验。

实验没有让一个测试程序直接伪造答案，而是安排了几个职责明确的角色：

  • 总控负责创建测试任务、推进阶段和汇总报告；
  • 测试用户以真实用户的方式发起消息或协同操作；
  • 被测数字员工保持正常工作配置，不为测试临时修改能力；
  • 测试员回读平台事实并评分；
  • WatchDog定时检查当前用例是否已经完成、失败或超时。

每轮测评有一个主任务，每个测试用例有自己的子任务。测试用户完成触发动作后立即退出，不占着一个任务一直等待。WatchDog 会在合适的时间回读真实结果；满足结束条件后，它通知总控进入评分和清理阶段。

一次简化后的过程大致是：

创建测试任务
  → 测试用户在专用环境发起真实操作
  → 数字员工响应或执行工作
  → WatchDog 回读平台结果
  → 测试员按证据评分
  → 清理测试数据和定时任务
  → 生成最终报告

这里最重要的一条原则是：以平台中可以重新读取的事实为准。

发送命令返回成功，不等于用户真的收到了消息；Agent 回复“已经写好”，不等于目标文档存在。只有重新读取消息、文档、日程等实际对象，才能把“看起来完成”和“真的完成”分开。

一次最小验证带来的启示

在一个基础消息场景中，整条链路已经可以在没有人工接手的情况下完成：创建测试环境、发起交互、等待回复、回读证据、评分、清理临时数据，最后生成报告。

被测数字员工在一分钟量级内完成了响应，而整轮测评用了二十分钟量级。这个结果很有意思：业务动作本身并不慢，主要时间花在身份检查、任务编排、定时检查、评分和清理上。

所以，这次验证证明的是无人值守测评在机制上可行，并不意味着测试效率已经足够高，也不意味着一个用例通过就能证明某个数字员工已经成熟。

下一步有两个方向。

一方面，业务团队需要继续沉淀用例：从岗位职责、用户反馈和线上问题中，逐步形成每个数字员工自己的测试库。

另一方面，工程侧需要提升测评效率和发布保障能力：复用同一批次的身份检查，并行执行互不影响的用例，让成功结果可以提前结束，并逐步把固定轮询改成事件触发、定时兜底。同时，将 Agent 版本、测试用例、自动回归结果和发布审批关联起来，让发布决定不再只依赖开发者的主观判断。

接下来会继续拆什么

我们现在更愿意把数字员工测评理解为一种“工作能力的持续证明”。

它不是上线前的一次考试，也不是一张静态分数表。岗位会变化，工具会变化，真实使用中还会不断出现新的问题。每一次经过确认的问题，都应该让测试集变得更完整；每一次发布，都应该重新证明那些关键能力没有退化。

这篇开篇先把方法说清楚。下一篇会从最容易被忽略的 L1 基础能力开始：群聊里什么时候该说话，多轮对话如何承接上下文，收到未来日程为什么不能立即执行。

再往后，我会继续拆解文档和日程等工作产物如何验证，无人值守 E2E 怎样运行，以及这些测试怎样成为数字员工发布前的质量依据。

先把这些基础问题测明白，再谈一个 Agent 能不能成为可靠的数字员工。
