Personal Agent 的说话语气：像懂行的朋友一样聊天

2026年10月13日
|

我希望 Personal Agent 像懂行的朋友：先给结论，接得上用户的知识背景，交付结果时只讲必要的过程。结合个性化研究与开源实践，讨论怎样让消息更可读。

如果要用一句话描述我希望 Personal Agent 怎么说话，我会说：像懂行的朋友一样聊天。

你把事情交给他，他回来能直接告诉你结果。你问一个自己熟悉的问题，他接得上，不需要从入门知识讲起；你碰到陌生领域，他又能把影响和选择解释清楚。有不同意见时，他会说理由，也知道哪些地方还拿不准。

Personal Agent 的消息，我希望也能做到这样。

它可能已经查完资料、改好文件，但最后返回一大段背景铺垫和工具流水账，用户仍得自己从里面找答案。另一种回复很礼貌、很完整，却像客服话术或课堂笔记，读完总觉得隔着一层。

我的判断是：要让 Personal Agent 的消息更可读，先守住几条通用原则，按用户对当前问题的熟悉程度交流，再控制执行细节的披露。下面的论文和开源案例提供了一些支持与边界；这三条仍是我对产品的要求，不能当作已经被统一验证的行业结论。

先把有用的话说出来

用户让 Agent 做一件事，回来看的第一条消息，应该先回答这件事。

完成了，就说完成了什么；只做完一部分，就交代哪些还没做；卡住了，就把阻塞放在前面。问的是判断，就先给判断，再补依据。

比如，让 Agent 审阅一篇草稿。以下回复都是示意，不对应真实任务。

一种常见的开头是：

我已经认真阅读了这篇文章，整体来看内容比较完整，结构也比较清晰。下面我将从几个方面进行分析，希望能帮助你进一步优化。

这段看起来周到，但用户还不知道最该改哪里。

我更希望它直接说：

观点已经清楚，主要问题是后半段的两个案例重复。建议删掉第二个，把第一个案例里的判断依据补上。

需要细看时，再给具体段落。这条消息已经足够让我接着做事。

“好的，我来帮你”“希望这对你有帮助”“如有其他问题请随时告诉我”，也不必成为每次回复的标配。认真回答、准确措辞、尊重选择，本身就有礼貌。没有信息的开头和结尾可以直接删掉。

但我也不想把这件事简化成一个字数上限。用户要深度调研、学习教程或故障分析，长文可能正是交付物。可以先用一小段说明判断和范围，再让读者进入细节。

评价模型时，长回答甚至可能得到额外的优势。Length-Controlled AlpacaEval 研究通过控制回复长度差，减轻自动评委对长回答的偏好。它支持的是“评分会受到长度影响”，并没有证明短回答总是更好，也没有直接测量结论是否应该放在首句。

对我来说，这个提醒很实际：不能因为回复显得充分，就认为它对用户更有用。应该看删掉一段以后，是否损失了用户需要的事实、解释或判断。没有损失的部分，就值得考虑删掉。

接得上用户的语境

懂行的朋友会知道哪些话可以直接说，哪些地方需要解释。

用户熟悉的领域，不要刻意说浅。开发者问数据库迁移，可以直接讨论迁移顺序、旧库兼容和验证范围；用户已经交代过的背景，也不必原样讲回来。

用户不熟悉的领域，则需要把术语转换成他能判断的影响和选择。复杂度可以留在依据里，消息先让他知道为什么要在意。

假设一次更新测试发现，软件没有正确读取老用户保存的设置。面对负责修复的工程师，可以说：

这版先别发。旧配置没有迁移到新路径，升级后会回到默认设置。需要补迁移，再用已有配置走一次升级测试。

面对只关心能否交付的用户，可以说：

这版先别发。老用户更新后，之前保存的设置会失效。先修好设置保留的问题，再确认更新后的设置还在。

两段都保留了判断和原因，解释的深度不同。照顾用户的知识背景，不能把关键影响一起删掉。

这里有一项很贴近的研究。ExPerT（ACL 2026） 按每次问题的领域知识调整细节、术语和概念复杂度。它的主研究有 40 名参与者，覆盖三个领域；按用户自报知识水平生成时，满意度从 3.71 提高到 4.36，满分为 5 分。

这个数字来自自报知识水平的条件，自动推断有另一组较小的回访实验。满意度也不等于理解正确率。研究还使用了打字行为等线索，我更想借鉴的是其中的判断方式：用户懂不懂，应该落到当前问题上。

一个工程师可能很懂数据库，却不熟悉设计。即使在同一个领域，赶着做决定和准备深入学习，需要的回复也不同。不能记住“这是个专业用户”，就默认他不需要任何解释。

拿不准时，也可以通过对话确认，而不是继续猜。2026 年 8 月公开的专业程度澄清研究 就探索了用有针对性的提问获取知识背景。它包含模拟实验和小规模角色扮演式真人评估，尚不能证明日常助手都应该主动提问。我倾向于只在答案确实会改变解释方式时问，例如：“你想了解原理，还是主要想判断对当前方案的影响？”已经有足够线索，就直接接着聊。

长期偏好和本次要求也要分开。Letta Code 的主提示词 把 persona 作为默认行为，同时允许用户本次对语气、格式和细节量的明确要求改变表达。这是一项提示词约定，不代表每次输出都会正确执行，也不是自动识别用户专业水平。

我认同这种分工。记住一个人平时喜欢简短回复，可以省掉重复沟通；他这次说“深入讲讲”，就应该展开。记忆应该帮助接上对话，别让它变成限制对话的旧标签。

不过，允许按当前需求调整，还不等于模型能稳定做到。9 月 28 日提交、9 月 30 日修订的一篇过度个性化预印本 发现，在其测试的模型与任务中，单独判断时能排除的偏好，到了生成回答时仍可能被用进去。它分析的是特定实验中的决策偏差，不能概括所有助手。对产品设计的提醒是：除了存下偏好，还要检查这一次是否应该应用。

对等交流还包括不同意。2026 年的 OP-Bench（9 月修订版） 已把不相关、重复和迎合作为过度个性化的不同评测任务。它使用经人工审查的合成数据，仍以英文单轮文本为主，不能替代中文用户的实际体验验证。但这种评测方向很值得借鉴：“让用户喜欢”之外，还要检查个人信息是否把回答带偏了。

所以我说的朋友感，也包含这样的回复：“这个方案我不建议，原因是……”或者“目前只能确认到这里，还不足以下结论。”不居高临下，也不为了显得亲近而附和。

交付结果，按需要交代过程

Agent 在执行任务时，可能读取文件、搜索资料、调用接口，也可能经历几次失败。交付消息里，不需要把这些动作逐项复述。

正常完成时，我更想看到这样的回复：

安装包能正常启动，已有设置也保留下来了。检查覆盖了安装和升级流程，账号登录还没有验证。

它交代了结果和验证范围，也留下了一个明确缺口。用了哪些命令、按什么顺序打开页面，可以放在检查记录里。

如果只说“先调用工具 A，再读取文件 B，重试两次后执行命令 C”，用户还得自己判断这些动作说明了什么。Agent 应该把对结果有用的部分提炼出来。

不过，过程有时就是用户需要的信息。出错、卡住、需要选择，或者发生了会影响结果的重要变化，就应该主动交代。例如：

最新公告暂时无法读取，发布时间还不能确认。草稿其他部分已经写好，这一处保留待核实标记。

用户知道缺口在哪里，哪些工作已经完成。除非正在排查访问问题，否则不必再附上每次重试。

这也是 《Challenges in Human-Agent Communication》 讨论的问题：一方面，细节过多会增加信息负担；另一方面，用户需要了解执行状态、重要副作用以及目标是否达成，才能核验和干预。这篇文章提出的是沟通挑战与研究方向，并不是“少播报胜过多播报”的实验。

它让我觉得，少讲过程还需要一个前提：用户想检查时，能找到记录。主消息尽量围绕结果组织，来源、差异和详细操作留在容易访问的位置。未完成事项和关键限制仍然应该直接可见。

OpenHands 的聊天界面 提供了一个具体例子：连续动作与观察可以折叠成可展开的摘要卡片，运行中仍显示最近动作和完成计数。它没有隐藏所有过程，一些消息和产物仍独立展示。

这是源码能确认的界面机制，尚不能据此判断用户实际觉得更好读。但它说明，减少过程占用不一定全靠模型少写几句话，界面也能承担信息取舍。

长任务同样需要进展消息。Claude Sonnet 5.5 的当前官方文档 已专门讨论面向用户的进展更新：部分更新通过单独的内容块返回，客户端只展示普通文本时，长任务可能显得没有反馈。这是特定模型的接口行为，也说明消息体验需要模型和界面共同处理。

所以我不会把“少讲过程”写成“正常执行时一直沉默”。用户需要知道它还在推进。更新最好带来新状态：完成了哪部分，发现了什么缺口，是否影响交付。反复说“正在努力处理”，很难帮助用户决定还要不要等。

需要用户选择时，则先把选择的影响讲清楚。已经明确授权的操作不用重复问；确实缺一个决定，就把问题停在那个决定上。用户主动要完整排查记录或审计材料时，按要求交付。

最后还是要看用户能不能接着做

这些要求可以写进提示词，也可以通过记忆和界面实现，但是否奏效，还得检查实际回复。

MyScholarQA 的研究（ACL 2026） 给了一个提醒：它在合成用户和模型评委的离线评价中表现良好，真人访谈却发现了九类未被覆盖的问题，其中就有夸大用户专业程度、偏离当前问题的个性化。这个结果来自科学文献调研场景，不能推到所有助手上，但足以说明离线高分之外仍要听用户的反馈。

如果要验证这套表达方式，我会拿同样的任务事实和结果，比较不同回复，再请目标用户回答几个问题：

  • 第一段读完，事情完成了多少、还有什么没做，是否清楚？
  • 解释的深度是否合适，有没有重复已知内容或跳过必要概念？
  • 如果结果里有缺口或错误，能不能识别，而不是只觉得回复很流畅？
  • 需要做决定时，能否直接选下一步，还是得再问“所以这对我有什么影响”？

这只是我建议的验证方式，还没有在某个产品上做出效果结论。字数、工具播报次数可以一起记录，但不能单独当成目标。删掉关键限制的极短回复，同样不合格。

我希望 Personal Agent 最终能让我省掉一件事：不用再替它整理一次答案。

像一个懂行的朋友，它知道我在问什么，接得上当前的语境，把结果和必要依据说清楚。需要深入时一起讨论，事情交代完就停下来。
